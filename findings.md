## Residual risk

1. **Ledger key custody and downgrade.** V5 entries are HMAC-SHA256 under `~/.sir/ledger.key`. An actor who can read that key can forge entries; deleting the key makes existing V5 entries unverifiable (reported as a clear error). The format still accepts V1–V4 so old ledgers verify, which means an attacker who can rewrite the whole file *and* knows the hash schedule can downgrade the chain; this is a local-tamper-evidence feature, not remote notarization. Back up the key with incident evidence.
2. **Sandbox egress is not closed.** `sir run` still permits `file-read*` of credential paths and DNS resolution via the system resolver (SEC-03). The unix-socket pivot for known host-control sockets is closed; other unix sockets remain available for legitimate app IPC. Linux `mcp-proxy` remains network-only (no filesystem/PID containment).
3. **Hook layer is lexical.** Newlines, `$(...)`, backticks, process substitutions, and unresolved command-position variables are handled, but a novel wrapper/POSIX construct can still evade classification. The OS layer remains the real boundary. The CLI confirmation gate reads the controlling terminal, which stops the normal agent Bash path (no TTY); an agent that deliberately allocates a pty and feeds its own answer is outside the same-user local-attacker scope already documented in the threat model.
4. **Unfixed team findings:** MCP injection heuristics/taint clearing (SEC-06), relay authentication (SEC-07), MCP-scope symlink escape (SEC-08), dead tripwire control (SEC-09), config-driven `--no-sandbox` (SEC-10), strict-posture `.mcp.json` auto-approval, Linux proxy write containment, terminal escape injection, `sir trace` temp file, `mister-core` PATH/blank-hash fallback, and SLSA provenance. Each is listed above as `DEFERRED`/`ACCEPTED RISK` with the recommended next step.
5. **Windows.** The repository documents Windows as unsupported; `GOOS=windows go build ./...` already failed at HEAD (`syscall.Flock` and process-group syscalls are Unix-only). This pass keeps darwin/linux (`amd64`/`arm64` where applicable) green and does not claim Windows support.
6. **Repository settings.** Enabling GitHub private vulnerability reporting (M-04) and adding security checks to the required-status-check ruleset (QA-08) cannot be done from the working tree; the owner must apply them in repository settings.
7. **Secret history.** The fixtures in git history are synthetic and were left untouched; no history rewrite was performed and no rotation is required. `gitleaks` now scans history in CI with a narrow fixture allowlist.
